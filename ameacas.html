Ameaças e defesas da aplicação web

Uma visão prática dos riscos para a CyberStore, com controles para proteger contas, pedidos e comunicação.

Laboratório educativo: o login usa dados fictícios definidos no JavaScript e não autentica ninguém. O bloqueio pode ser reiniciado ao recarregar a página. Em produção, autenticação, limite de tentativas e autorização precisam ser aplicados no servidor.

Credenciais fictícias para este exercício: cliente@exemplo.test / Cliente123! e admin@exemplo.test / Admin123!. Após três falhas, use o botão para reiniciar a simulação.

Teste educativo de autorização

Esta demonstração usa regras locais e não acessa pedidos nem produtos reais. Em uma aplicação, a decisão precisa ser repetida no servidor.

4. Recuperação de conta (simulação)

Informe um e-mail fictício. A interface sempre mostra a mesma resposta, sem confirmar se existe uma conta. Nenhuma mensagem é enviada neste protótipo.

Como proteger esse fluxo no servidor

  • Responder sempre com uma mensagem genérica, como “Se houver uma conta associada, enviaremos as instruções”, tanto para e-mails existentes quanto inexistentes.
  • Limitar requisições por IP e por identificador de conta com uma janela de tempo, armazenando contadores em serviço compartilhado entre instâncias. Ao exceder o limite, aplicar espera ou resposta HTTP 429 sem revelar se a conta existe.
  • Gerar um token aleatório, de uso único e curta validade; armazenar apenas seu hash e invalidá-lo após uso ou expiração. Não enviar senha por e-mail.
  • Registrar e monitorar tentativas sem guardar tokens ou expor dados pessoais nos logs. A tela local não implementa esses controles.
